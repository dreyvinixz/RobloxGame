## Implementation

- The scout chassis is authored from Roblox primitive Parts in `VehicleService`; no Creator Store model, paid asset, external package, or embedded script is used.
- All chassis parts are anchored. The server moves the model with bounded `PivotTo` steps, clamps `dt` to 0.1 seconds, speed to 24 studs/s, acceleration to 14 studs/s², checks three forward rays, and stops at arena bounds.
- The client sends only normalized throttle/steering intent. The server verifies the active driver, occupant, finite inputs, exact argument count, packet cadence, and stale-input timeout. It ignores client positions and CFrames.
- Enter uses an E ProximityPrompt with server-side distance and occupancy validation. E exits. The client camera follows the vehicle PrimaryPart while driving and restores the character subject on exit.

- Synced the branch sources into Roblox Studio and started Play. The server log confirmed the vehicle service; the client log confirmed the controller.
- With the character repositioned within 5 studs, the real `VehicleAction` remote entered the seat. Server state confirmed the correct Humanoid occupant and `DriverUserId`.
- The client camera subject changed to the vehicle PrimaryPart and returned to the current Humanoid on exit. The exit remote cleared the seat; server state ended at `DriverUserId=0`, speed 0, and no occupant.
- With the ordinary input sender paused only for an isolated probe, 12 normalized forward inputs at 0.05-second intervals moved the replicated chassis 4.31 studs; observed speed was 10.9 studs/s. Inputs of 999/999 were clamped; observed speed remained below the configured 24-stud/s limit (23.3 at the sample). The ordinary controller script was restored enabled after the probe.
- This was a one-client Studio remote-driven probe, not a keyboard-recorded route. Reverse/braking/steering as a complete route, obstacle stopping, arena-edge behavior, a second-client observer, and route video remain unverified.
