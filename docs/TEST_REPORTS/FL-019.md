# FL-019 — Multiplayer combat security (partial)

**Date:** 2026-10-15  
**Environment:** Roblox Studio Place1, `StudioTestService.ExecuteMultiplayerTestAsync(2, "FL019_Acceptance")`, one simulated server and two clients.

## Runtime result

The synchronized harness completed with:

```text
PASS | fire validation, valid damage and reload spam throttle | reload responses=2
```

The test placed two players on opposing teams, waited for spawn protection to expire, submitted malformed/extra-field and extra-argument fire requests followed by a valid shot, then sent 50 reload requests rapidly. The valid shot caused damage and the nonlethal hit left team score unchanged. The reload burst yielded two `WeaponState` responses.

The harness did not record an HP snapshot between invalid requests and the valid shot, so it does not isolate whether invalid requests left HP exactly unchanged. It also did not compare HP simultaneously on both clients, and Studio simulation did not vary real network latency. Those acceptance checks remain open.

Later attempts added an HP-before/after assertion, but the Rojo connection had disconnected and Studio continued running the prior harness version. Those attempts are excluded from the result above. Temporary harness scripts were removed from the root checkout; no harness is committed.

## Static review and code change

`CombatRequestService` checks exact payload keys, finite vectors, allowed weapon ID, unit direction, direction/target consistency, range, origin proximity, fire interval, and rejects extra remote arguments. `DamageService` derives damage from server-side weapon configuration. FL-019 adds a per-player reload interval of 0.25 seconds and clears that timestamp when the player leaves.

## Remaining acceptance work

- Capture target HP before and after only invalid fire requests.
- Compare the target's HP from both clients after valid and invalid requests.
- Repeat under a documented latency variation before claiming different-latency coverage.

## Validation

Local validator, Python unit tests, Rojo build, and `git diff --check` are recorded in the PR. Runtime evidence is limited to the checks described above.
