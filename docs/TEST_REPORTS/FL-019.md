# FL-019 — Multiplayer combat security (partial)

**Date:** 2026-10-15  
**Environment:** Roblox Studio Place1, `StudioTestService.ExecuteMultiplayerTestAsync(2, "FL019_Acceptance")`, one simulated server and two clients.

## Runtime result

The synchronized harness completed with:

```text
PASS | fire validation, valid damage and reload spam throttle | reload responses=2
```

The test placed two players on opposing teams, waited for spawn protection to expire, submitted malformed/extra-field and extra-argument fire requests followed by a valid shot, then sent 50 reload requests rapidly. The valid shot caused damage and the nonlethal hit left team score unchanged. The reload burst yielded two `WeaponState` responses.

That first harness did not record an HP snapshot between invalid requests and the valid shot, so it did not isolate whether invalid requests left HP exactly unchanged. It also did not compare HP simultaneously on both clients, and Studio simulation did not vary real network latency. A later isolated retry below covers the HP and client-replication checks but still does not vary latency.

Later attempts added an HP-before/after assertion, but the Rojo connection had disconnected and Studio continued running the prior harness version. Those attempts are excluded from the result above. Temporary harness scripts were removed from the root checkout; no harness is committed.

## Isolated local Play follow-up — 2026-10-15

A normal one-client Studio Play run isolated the cause of the earlier unchanged HP: from the harness position at `(0, 10, 0)`, the server raycast first hit `Workspace.FL013_TestArena.Test_Garbage_Bin_01.Garbage_Bin_01` at about 21.19 studs, before the TrainingDummy. Moving the shooter to the unobstructed lane at `x=-15` made the same valid shot reach the target.

With the shooter at `x=-15`, three invalid requests (an extra `damage` field, an extra remote argument, and a forged origin) each left TrainingDummy at 100 HP. A subsequent valid rifle shot changed HP from 100 to 75 on the client and server; the Azul score remained 0. This validates those request cases in a single local client session only.

The lane correction explained the earlier failed shot and allowed a reliable local check. The multiplayer retry below extends this evidence. The later TTK/falloff measurements are recorded in FL-020 and are local-session observations, not multiplayer acceptance.

## Two-client isolated retry — 2026-10-15

The recovered Studio runner completed `StudioTestService.ExecuteMultiplayerTestAsync(2, "FL019_Retry_Full_v2")` with:

```text
PASS | invalid payload HP, two-client replication, nonlethal score, reload throttle | 4 responses
```

The server placed the shooter at `x=-15`, the previously verified unobstructed lane. Three invalid requests (extra damage field, extra remote argument, forged origin) left the shooter client's target HP at 100 after each request. The following valid rifle hit changed target HP 100→75; the server and observer client both reported 75, and the nonlethal hit did not change Azul's score. A burst of 50 reload requests produced four `WeaponState` responses, far fewer than the request count and consistent with the 0.25 s server throttle.

This covers two-client damage replication, invalid payload resistance, score stability, and reload spam in Studio's simulated network. No explicit latency variation was applied; tests under differing latency remain pending.

## Static review and code change

`CombatRequestService` checks exact payload keys, finite vectors, allowed weapon ID, unit direction, direction/target consistency, range, origin proximity, fire interval, and rejects extra remote arguments. `DamageService` derives damage from server-side weapon configuration. FL-019 adds a per-player reload interval of 0.25 seconds and clears that timestamp when the player leaves.
