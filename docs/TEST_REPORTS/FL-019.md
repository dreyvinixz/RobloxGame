# FL-019 — Multiplayer combat security (partial)

**Date:** 2026-10-15  
**Environment:** Roblox Studio Place1, `StudioTestService.ExecuteMultiplayerTestAsync(2, "FL019_Acceptance")`, one simulated server and two clients.

## Runtime results

The first `StudioTestService.ExecuteMultiplayerTestAsync(2, "FL019_Acceptance")` run completed with:

```text
PASS | fire validation, valid damage and reload spam throttle | reload responses=2
```

A later owner-reported two-client retry (recorded in the issue comment) strengthened coverage: extra `damage` payload field, extra remote argument, and forged origin each left shooter-side HP at 100; a valid hit changed server/client HP 100→75, the observer also reported 75, and score remained unchanged. Fifty reload requests yielded four `WeaponState` responses. The earlier unchanged-HP result was caused by a garbage bin blocking the harness lane; the retry used a clear lane.

## Latency attempt — not completed

I verified Studio `NetworkSettings` accepts a temporary 120 ms inbound and 120 ms outbound minimum delay with 20 ms jitter in each direction. The subsequent `ExecuteMultiplayerTestAsync(2, "FL019_latency_inout120_jitter20")` call failed before launch with `Failed to start the test because a previous one is still in progress.` Studio reported Edit mode while several other connected Studio processes were in live two-client FL-023 sessions. I did not interrupt them. The temporary harness and source sync were removed/restored exactly, the network settings were reset to zero, and Place1 returned to Edit. No latency-conditioned gameplay result is claimed.

## Static review and code change

`CombatRequestService` checks exact payload keys, finite vectors, allowed weapon ID, unit direction, direction/target consistency, range, origin proximity, fire interval, and rejects extra remote arguments. `DamageService` derives damage from server-side weapon configuration. FL-019 adds a per-player reload interval of 0.25 seconds and clears that timestamp when the player leaves.
